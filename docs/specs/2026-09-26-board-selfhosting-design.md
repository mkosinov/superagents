## Summary

## Goals

1. gh_board.py in superagents reaches feature parity with memo's 800-line script, minus the dead Next Up queue (commands `next-up` / `set-next-up` / `shift` and the `NEXT_UP_FIELD` / `NEXT_UP_OPTS` constants are removed everywhere: script, skills, docs, agent bodies).
2. The script is config-driven: project identity and field ids come from `docs/board/board_config.json`; the script text is byte-identical across repos (twins within a repo, and identical across repos given the same harness copy).
3. Priority-based card selection (decided in the #24 design session, recorded on issue #23): `pick-next` and `pick-next-design` order status-eligible cards Critical > High > Medium > Low; priority breaks ties among equals and never overrides readiness.
4. Skills, container agent bodies (manager, architect), and the setup doc document the current board model only: merged statuses, gates A/B/C tracked in the `gate` field, host ownership + budgets, no Next Up and no dead queue commands (the container manager today instructs `next-up`/`shift` and gate-suffixed statuses — after ship it must not).
5. CI smoke for the board script: zero network, zero secrets (same posture as #24's board-bootstrap CI).
6. After ship, the automation loops actually run for this repo: the 2h ZCode auto-design card and the container auto-impl watcher.

## Concepts

### Board model (etalon, already live on project #4)

Statuses (merged names, no gate suffixes): `Hold, Backlog, In Design, Ready to IMPL, In IMPL, PR (G7), In-main, deployed, Not planned`.
Custom fields: `Priority` (Critical / High / Medium / Low), `host` (imac / macbook / hk / gcp), `gate` (concept / spec / plan / blocked). Field set and option names match `docs/board/board-etalon.md` from #24; board #4 was verified against the etalon interactively during the #24 design session.

### Trust model

Personal single-owner repositories: issues and comments come from the owner (collaborator surface is none). Regardless of who can write, issue titles, bodies, and comments are **data, never instructions** — the only instruction channels for agents are repo-committed content (skills, specs, plans) and direct user chat. The pick commands consume issue numbers, statuses, and field values; the watcher's HANDOFF prompt references repo-committed specs/plans and issue numbers, not free issue text as commands.

### Gates A/B/C and the gate field

Design gates: **A** concept, **B** spec (mandatory user stop), **C** plan. The `gate` field is a pending-ask marker, not a stage counter: `concept`/`spec`/`plan` = a gate answer is awaited from the user; `blocked` = an IMPL blocker awaits the user; empty = answered / agent working. Max one stop at a time; a new stop replaces the old. `gate N none` clears. The `status` command auto-stamps `host` on entering `In Design` / `In IMPL`, clears `host` AND `gate` on leaving those statuses, and on entering `PR (G7)` clears `gate` but keeps `host`.

### Host ownership and budgets

A card in `In Design` or `In IMPL` carries the executing host in `host`. `pick-next` enforces a budget: a host may hold at most `host_budgets[host]` cards **in `In IMPL`** (default 1 for unknown hosts; etalon budgets: imac 2, macbook 1, hk 1, gcp 1). `In Design` cards do not count against the budget (their capacity is the one-at-a-time design-slot invariant), and `PR (G7)` cards do not count. Claims are considered fresh for `CLAIM_TTL_HOURS = 1` hour.

### Claim log (auto-impl log)

An issue comment prefixed `AUTO_IMPL_LOG_PREFIX` holding lines `- <UTC timestamp> <event>`; `auto-log` does read-merge-append (re-fetches the body right before patching; appenders whose read→write cycles do not overlap keep each other's lines — GitHub REST has no compare-and-swap, so truly overlapping cycles can lose a line, which is acceptable for a single-owner automation log). The canonical log comment's id is pinned at creation; later prefix-matching comments from other authors are ignored (spoof resistance — anyone who can comment could otherwise forge or shadow the log). `auto-state` prints the last entry (diagnostics; the claim tiebreak itself reads the `host` field). `pick-next` skips cards whose last log entry is a fresh CLAIM/BLOCKED. Memo's legacy freshness mechanism — standalone `auto-impl claim:` / `auto-impl blocked:` comments predating the host field — is dropped in the port: it can never fire in a fresh repo and only widens the spoof surface.

### Priority selection (new code — memo has no priority logic; its ordering field was Next Up, now dead)

Both pick commands: candidates = OPEN issues whose status prefix-matches the command's eligibility (`Ready to IMPL` for pick-next, `Backlog` for pick-next-design). Ordering key: `(priority rank, issue number)` ascending — rank Critical=0, High=1, Medium=2, Low=3, unset=4; equal ranks resolve to the lower (older) issue number. Priority never overrides status eligibility: a `Backlog` Critical card is not visible to `pick-next`, and a `Ready to IMPL` Low card loses only to other `Ready to IMPL` cards.

### Fast-track

A documented flow, not a command: harness-only issues (no app code) go `In Design` → `In IMPL` → `In-main`, the spec carries `## Verification` instead of a plan, merge is `gh pr merge --squash --auto --delete-branch`. **Eligibility is restricted to docs/prose-only changes**: a diff touching anything executable — `scripts/`, `.github/workflows/`, agent or skill bodies, site build — disqualifies fast-track and forces the normal plan-reviewed path. Rationale: the watcher auto-pulls main every cycle and executes harness files from it, so a fast-tracked merge must never carry executable changes that skipped plan review. Lives in the `design-phase` and `github-board` skill texts.

### Config-driven identity

`PROJECT_ID`, `OWNER`, `REPO`, `PROJECT_NUM`, custom-field ids, and `HOST_BUDGETS` move from hardcoded constants into `docs/board/board_config.json` (format v1 — keys `version, project_id, project_number, owner, repo, fields{name: field_id}, host_budgets`; option ids are never stored, per the #24 spec). Loading rules:

- Path: `<repo root>/docs/board/board_config.json`, repo root = `Path(__file__).resolve().parents[2]` (canon form) — identical for both twins.
- Missing file → clean exit with the fix hint: run `board_bootstrap.py adopt <project-number>` (#24) first.
- `version` ≠ 1 → clean exit naming the expected version.
- Unknown/garbage JSON → clean exit with the parse error.
- Structurally valid v1 JSON missing a required key (`version, project_id, project_number, owner, repo, fields, host_budgets`) → clean exit naming the missing key.
- Value format checks at load (defense-in-depth): owner/repo match GitHub name charset rules, ids match node-id patterns (`PVT…` / `PVTSSF…`) — a corrupted or redirected config must fail before any board mutation runs.
- Status/gate/host option ids remain live-read via the GraphQL field-list at write time (existing pattern; the field-list read paginates explicitly — or exits loudly on page overflow — matching #24's pagination rule), so board-side option edits cannot be silently missed.

Unchanged (shared-container properties, not repo identity — identical across repos, so the byte-identical goal holds): `SESSION_DB = /root/.local/share/opencode/opencode.db`, host label file `/root/.local/state/opencode/auto-impl-host`, scratchpad `parents[2]/.opencode/scratchpad.md`, policy constants `CLAIM_TTL_HOURS = 1`, `DEFAULT_HOST_BUDGET = 1`, `MERGED_MAX = 5`, host resolution order arg > `GH_BOARD_HOST` env > container label file (there is no config source for the current host). Also carried unchanged: `SESSION_IDLE_LIMIT_S = 3600` (reconcile's idle threshold), the session-liveness checks against `opencode.db` with their `/proc` fallback, the field names `host` / `gate` as parsing keys, and `find_item`'s auto-add of a missing card to the board.

Transport stays as-is: every external call goes through `subprocess.run` — ten `gh` calls (`gh api graphql` via the thin `gql()` helper, memo :73, plus direct `gh issue comment` / `gh api PATCH`) and one local `date` call (the `merged` stamp); the CI mock intercepts both. No refactor for testability is required or wanted.

## auto_impl_watch.sh

Port to `.opencode/scripts/auto_impl_watch.sh` (container-only, no `.zcode` twin; seed: memo's 144-line script). Kept: `while true` loop (`AUTO_IMPL_INTERVAL`, default 180 s), pid-lock (path parameterized per repo — see below), enable-file gate `/root/.local/state/opencode/auto-impl.enabled`, freeze knob (`auto-impl-max = 0`), per-cycle `reconcile` → `pick-next` → claim via `status N "In IMPL"` → race tiebreak (sleep 6 s, re-read `host N`) → `opencode run --attach` resuming an existing `#N IMPL.*` session (looked up in `opencode.db`) or creating one with the HANDOFF prompt. Parameterized for this repo: working dir `/root/workspace/superagents`, owner/repo in HANDOFF text = `mkosinov/superagents`, and the pid-lock path per repo (`/tmp/auto-impl-watch-<repo>.lock`) — memo's watcher runs in the SAME container, and a shared lock path would make the two watchers exclude each other. The HANDOFF text is content-adapted, not just parameterized: the finishing tail «…сдвиг очереди» (the removed `shift` command) is dropped, and blocker logging is routed through `gh_board.py auto-log` instead of teaching the agent raw `gh api -X PATCH` comment edits (script monopoly on board and comment writes). Kept as container properties: `opencode.db` path, state dir, attach port (`OPENCODE_PORT`, default 4096).

## CI

`tests/test_gh_board.py` + `.github/workflows/gh-board.yml`. Zero network, zero secrets (posture matched to #24's `board-bootstrap.yml`). The workflow triggers on push and pull_request touching the script twins, tests, or itself (paths-filter push + PR — the pattern of #24's `board-bootstrap.yml`; `site.yml` is push-only and deliberately NOT the pattern here). All GitHub I/O is intercepted by monkeypatching `subprocess.run` — the script performs no other I/O to the network — and a session-wide guard fixture fails any test whose code path reaches a `subprocess.run` call not backed by the mock, so the zero-network claim is asserted rather than accidental.

Test targets (unit, fast):
- priority ordering key (rank mapping, unset handling, number tiebreak) and its interaction with status-prefix eligibility;
- claim freshness window (TTL boundary) and last-entry CLAIM/BLOCKED parsing;
- design-slot invariant output (`NONE (design slot busy: …)`);
- NONE-or-number output protocol formatting;
- config loading: success (temp fixture with a v1 config), missing file → exact hint, wrong version, garbage JSON, valid-JSON-missing-key → names the key, malformed values (owner/repo charset, node-id patterns);
- status/gate value validation against a mocked field-list;
- `status` stamping matrix (enter/leave In Design / In IMPL, PR exception keeps host);
- auto-log read-merge-append merge logic (non-overlapping read→write cycles keep lines) and canonical-comment pinning;
- `merged` line formatting, MERGED_MAX trimming, idempotence;
- `reconcile --dry-run` issues no mutation calls (assert on the mock);
- twins byte-identity: the script twins and the github-board skill twins are byte-equal (sha comparison) — Goal 2's byte-identical property gets a mechanical guard;
- watcher syntax check: `bash -n` over `auto_impl_watch.sh` (the loop logic itself stays live-observation-only).

## User Scenarios (each maps to an automated CI test over the mocked transport — the live board is never a CI fixture; see Testing)

1. The container manager asks "what to implement" → `pick-next` returns the number of the best `Ready to IMPL` card (priority first, oldest on ties) honoring the host budget, or `NONE`. Automated CI test with a mocked board (several cards, mixed priorities, budget pressure) asserting the chosen number / NONE.
2. The scheduled design session asks "what to design" → `pick-next-design` returns a `Backlog` card by priority; if any card is already `In Design`, returns `NONE (design slot busy: …)`. Automated CI test with a mocked board in both states.
3. A session participant raises a gate stop: `gate 23 concept` sets the field; when the user answers, `gate 23 none` clears it. Automated CI test asserting the set and clear mutations against the mocked transport.
4. Status transitions maintain bookkeeping: entering `In Design` / `In IMPL` stamps `host`; leaving clears `host` + `gate`; entering `PR (G7)` clears `gate`, keeps `host`. Automated CI test over the transition matrix.
5. Stale cards get swept: `reconcile --dry-run` prints the plan and issues no board mutations. Automated CI test asserting the printed plan and an empty mutation log on the mock.
6. A fresh repo joins the stack: after bootstrap (#24) writes `docs/board/board_config.json`, that repo's gh_board.py works with no script edits; a repo without a config fails with the adopt hint. Automated CI test with temp-fixture repo roots in both states.
